### 2026-10-06 — condensed to current truth

The row's full Detail text before condensation, verbatim (it holds the superseded and struck-through text, measurements, dated corrections and audit narrative that left the row):

The dataset models one Rover per element and the female build is used throughout (maintainer, 2026-07-29), enforced in `map-timings.mjs` by rewriting `MaleM/`->`FemaleM/` and `Nanzhu`->`Nvzhu`. That covers the DIRECTORY only, and the female build RENAMES moves: Aero's `AM_Attack10`/`AM_Attack11` are `AM_W_Attack10`/`AM_W_Attack11`, `AM_W_Attack05_1` drops its suffix, and Spectro's male `AM_LimitAtatck_01` is the female `AM_LimitAttack_01` with the game's own typo fixed. Five keys kept MALE animations that way, three in reference rotations of Rovers that appear in ranked teams. The fallback therefore matches on the game's own identity — the two genders' montages of one move apply the SAME damage ids — with a name normalisation (`_W` infix, the `Atatck` typo, a trailing `_1`) to break ties, because a move and its `_Child`/`_Rogue` variants SHARE that signature and matching on ids alone reproduces the arbitrary pick. The ROW properties must follow the substitution (`ROVER_MIRROR_RID`): `rowsByAsset` is keyed by the raw rid and the female asset is filed under the FEMALE rid, so a mirrored montage looked up under the male one misses — measured, it cost Aero's Heavy Attack its stamina (25 -> 0) and interrupt level (2 -> 4). What is NOT a gender defect: the damage table. Each element ships ONE table under whichever id the game filed it (Electro/Aero under the male id, Spectro/Havoc under the female), and `hit-map.json` already resolves 1501 -> 1502 rows, so the canonical id is a KEY and cannot move a number. Nor is `gauge-income.json`'s male/female split: the rows are identical in `buffId`, `attribute`, `channel`, `policy`, `magnitude` and `effect`, differing only in `skillId`, `table` and `skillName` — the male rows even cite the FEMALE-prefixed `buffId` — so the skill-join's refusal of 1310/1408/1502/1605 is correct for THOSE ROWS. ~~And the remap once proposed for it would have double-counted.~~ **That half was wrong, and an adversarial re-audit caught it (2026-09-18).** It is true of the gauge rows and false of the ID SPACE, which is what OPEN-ITEMS 38 actually named: `hit-map.json`'s entry for the dataset's **1501** holds 17 hit ids that are every one **1502**-prefixed, because the damage table the game files for Spectro lives under the FEMALE id. `build-skill-join.mjs` built `knownRowIds` from the DATASET rid, so `resolveSkillId` matched **0 of 17** against 1501's rows and **14 of 17** against 1502's — route 1, the strongest, was entirely DEAD for her (3 joined rows against 29/15/21 for the other three Rovers, with her `基础普攻1..4`, `蓄力1` and Liberation rows all refused as "no key owns this row's ids"). `rowSourceRidOf` now takes the row set from the id space the hit ids themselves name, requiring a UNANIMOUS prefix so a mixed set keeps the dataset rid rather than joining half a resonator against a stranger's rows; measured, Spectro goes 3 -> 14 (9 by exact damage id) with **zero** non-Rover rows changed. The gauge lookup follows the same map, so 1502's gauge rows resolve under 1501 — the remap item 38 wanted, RECOVERING rather than doubling precisely because the join is now keyed in the 1502 space and 1501's own rows are no longer walked. Two corollaries. The refusal reason `no DT_SkillInfo row for this resonator` was FALSE for all 11 rows it labelled — every one exists in `timing-data.json`; the join is built over the roster while the coverage loop walks every gauge-income rid, so a non-roster rid fell to a hardcoded else-branch stating a cause nobody had checked. And the DT_SkillInfo tables are NOT mirrors even though the gauge extract is: 1309/1310 and 1406/1408 match 43/43 and 23/23, but 1501/1502 is 30/42 and 1604/1605 has 5 non-matching rows each way — so "pure mirror" is a property of `gauge-income.json`, never of the underlying tables. **A follow-up audit (2026-09-21) re-verified all three of that commit's own residual risks and found one more defect, real but not yet live.** `map-timings.mjs` has its OWN table of the same name, `ROVER_MIRROR_RID`, used for a different join (recovering `staminaCost`/`interruptLevel` for a substituted montage); its fourth entry was `{1605: 1604}` — BACKWARDS. Havoc is the one element where the dataset kept the FEMALE numeric id (1604) as canonical, so the lookup is always `ROVER_MIRROR_RID[1604]`, which resolved to `undefined` — the entry that's actually reachable had no mirror at all. Fixed to `{1604: 1605}`; verified a byte-exact no-op on the committed export (only `generatedAt` moved), because 1604's own rows already answer every current key without the fallback — the bug was latent, mirroring a safety net the other three elements already had rather than the live regression Aero once suffered. The name-normalisation tie-break was re-attacked for roster-wide collisions and found safe: it only ever fires on 16 of 166 Rover montages (the rest resolve by an exact mirrored `byPath` first), every one of those 16 narrows to exactly one candidate, and the one genuine name+signature collision in the data (`AM_Execute01`, shared across all four elements) is doubly unreachable — `byPath` shortcuts past it, and it isn't in `hit-map.json` at all — with `null` (safe fallback to the male asset) as the design's own answer to a hypothetical future collision. A completeness sweep of every other Rover id/gender hardcode outside these two files found nothing at risk, but surfaced a FRAGILITY worth stating: `src/data/storage.js`'s saved-rotation/echo preset keys, and every curated JSON file's Rover entry, depend entirely on `preprocess.mjs` always keeping the LOWER numeric id as canonical (true today for all four pairs, verified) with no migration path if that direction ever flipped. Finally, of OPEN-ITEMS 38's 11 "no DT_SkillInfo row" refusals, 7 really are "mirror of an already-resolved id" as documented — but a fresh, DIFFERENT gap surfaced in the other 4: Aero's `1406009`/`1406101`/`1406203` stay refused because `keysByMontage` only indexes `genderMirroredFrom`, which `toFemaleRover` stamps ONLY when it performs the male-to-female substitution itself. `heavy_heavy_attack` resolves to its female asset directly through route 1's bullet chain — no substitution ever runs, so no stamp exists — and `timing-data.json` cites those rows' animation by its MALE name, which is now nowhere in the montage index. A code comment in `build-skill-join.mjs` claiming this class was already fixed for `1406009`/`1406101` was itself wrong and has been corrected. Zero runtime effect either way, since the gauge-income lane is unwired

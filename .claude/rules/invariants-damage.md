# Invariants — Buckets, crit, DEF/RES, attribution, damage rows

Breaking any one silently corrupts sim output. Code comments cite these as
`CLAUDE.md, "<title>"`, so keep the titles stable.

| Invariant | Detail |
| --- | --- |
| DMG-type (`formulaType`) is DATA-DRIVEN | Each raw damage instance carries the game's own type tag (`skill.damage[*].type`: 0 basic, 1 heavy, 2 liberation, 3 intro, 4 skill, 5 Echo Skill). `preprocess.mjs` maps each display row to its exact instances (`matchRowHits`, full rate-vector) and reads `formulaType` from them — NO kit-text parsing. Node `skillType` stays mechanical. Type 5 keeps the mechanical `baseFormula` as `formulaType` (there is no Echo level table) and states its ATTRIBUTION separately — see the attack-type-bucket invariant below; `isEchoSkill` remains as the flag |
| An underivable stack count is ONE, and says so | `scaleEffect` resolves stacks from the user's count → a curated gauge → a `castMatch` trigger → else **1 stack + `stacksUnknown`**. NEVER fall back to `maxStacks`: a real cap makes that a large silent assertion (Lynae is 55%/stack to a cap of 25) |
| An UNSCOPED `multiplierUp` multiplies the WHOLE kit | `resolveChainInherentContext` adds it for every hit when the effect names no keys and states no category (`buffs.js`). With `defaultActive` + `window.type: 'always'` that is a permanent, silent multiplier on everything the wielder throws — Cantarella's S2 read 2.45 on `basic_1` from a clause naming only Jolt, inflating every unrelated hit 3.45×. Six shipped that way. This is INFLATION, so it makes a character look BETTER and nothing about the output looks wrong. `tests/multiplier-scope.test.mjs` guard 1 keeps that set at zero |
| The BUCKET comes from the game, not from the sentence | `computeDamage` composes `(1 + dmgBonus) * (1 + amplify) * (1 + deepen)`, and the client's own `CharacterDamageCalculations.js` has the same shape: `t = 1 + Proto_DamageChange + elementBonus + attackTypeBonus` is ONE additive factor, while `Proto_SpecialDamageChange` and the target's `Proto_DamageReduce` are separate multiplicative ones. Which bucket a value lands in is NOT recoverable from kit text, because the game does not decide it from the wording — Sigrika's "targets take 30% more DMG" is SpecialDamageChange (multiplicative) and Cartethyia's "take 30% more DMG" is DamageChange (additive), same words. `data/buff-facts.json` is therefore the PRIMARY source and the text parse the fallback; the extractor drops any value whose bucket differs between two buffs of one owner rather than guessing. `multiplierUp` is never retargeted — it is the skill's own rate, not a bonus bucket |
| A chain's extra hits are DATA; whether they ADD is not | The game ships a Resonance Chain's own damage instances as bullets marked 共鸣N whose rows are already in `damageTable` — `matchRowHits` never attaches them, because the kit's display rows describe an S0 build (111 such rows, 20 resonators). But most chain-marked bullets REPLACE a hit rather than add one (84 of 106 measured), and adding a replacement inflates a character instead of merely understating them. The name test (strip 共鸣N, look for an unmarked sibling) only produces CANDIDATES: spot-checking all 16 against their own chain node found Cantarella's S1 "finisher" and Phoebe's S6 heavies to be upgrades whose base bullet is simply named differently, and Zhezhi's real extra Ivory Herald to resolve onto the wrong parent. So an entry ships only from `KIT_VERIFIED` in `chain-extra-hits.mjs`, with the node text quoted. Within a `family` the highest chain level at or below the build's SUPERSEDES the rest — Xiangli Yao's matrices exist at 共鸣1 and 共鸣6, and an S6 fires six, not twelve |
| An element WINDOW pays its own element, and nothing else | `applyBuffsToSteps` accumulated every element window into ONE `elementBonus` with a last-wins `elementId`, then tested each hit against that single id. Wrong in both directions: a hit matching the LAST element collected every other element's bonus too, and a hit matching an EARLIER one collected NOTHING. The second is what bit — Verina S4 grants her team +15% Spectro, and that alone silenced Hiyuki's own +30% Glacio window, **-39% on the carry and -33.1% on the team from a node that only ADDS**. It was also ORDER-DEPENDENT, so the same team could score differently for no reason a user could see. Element bonuses accumulate PER ELEMENT now, exactly as `dmgTypeBonus` beside them always did. Roster-wide this moved 55 of 378 teams (41 up, 14 down, median +6.14%, max +46.48%) and **52 of the 55 are mixed-element**, which is the only shape the bug could touch. Found by the Sequence Node Evaluation, not by any lock: no meta team holds a member above S0, so no generated artifact could ever contain the second element window that triggers it |
| A scoped AMPLIFY has a per-hit home, and a CAP branch is not a grant | `foldExternalGrants` placed a scoped DEF-ignore or RES-shred into `targetMods` with its scope intact, then dropped **every other** scoped grant into `unplaced` — a field nothing reads — on the docblock's claim that "the stat buckets are whole-build numbers" and "no weapon needs this today". Both halves were false: **10 scoped amplify grants ship across 8 weapons**, and the per-hit lane already existed and was already fed by the sibling grant of the SAME weapon — `sim.js weaponAmplifyScopes` turns `amplifyByElement`/`amplifyByType` into per-hit scopes and `skill.js` matches them against each hit's own element and attribution, byte-identically to `targetModApplies`. `emptyContribution` and the `stats.js` team merge had the buckets; only the fold's own `emptyBuckets` lacked them, so `assignBuckets` had nothing to copy. Four weapons lost the grant ENTIRELY — the data lane wins on an unrelated row, so `hasPlaceableValue` suppresses the text fallback: Spectral Trigger 30% Heavy, Daybreaker's Spine 20% Basic, Lethean Elegy 32% Echo, Bloodpact's Pledge 10% Aero team-wide. What the rows do NOT say is which is a GRANT and which a CAP: Lux & Umbra ships +24% scoped to Heavy, +24% to Echo Skill and +24% to BOTH — the tooltip's "capped at 24%" as three mutually-exclusive `BuffAction` branches, which summed reads **72%**. OVERLAPPING SCOPES ARE THE SIGNATURE (two grants that can both pay one hit are alternatives, or the game double-pays the overlap), so a source whose scoped amplify grants overlap has ALL of them refused and falls through to the text reader. Refusing the whole set, not the colliding pair, is deliberate — a partial placement makes `hasPlaceableValue` true and silently suppresses the fallback that carries the refused half. A scope naming both dimensions, or one whose damage tags are all unmapped (`scopeOf` filters those and leaves an EMPTY list, which every reader treats as "everything"), is refused for the same reason the crit lane refuses one. Measured: 7 of 8 weapons now place, Lux & Umbra alone stays; 65 of 406 meta teams moved (52 up, 13 down), **all 65 containing a member who equips an affected weapon and zero without one**, and **no anchor's best team regressed** (14 improved) — the 13 drops are lower-ranked teams where a re-geared member's new weapon fits worse, which is the known one-build-per-character limitation, not a loss |
| A SCOPED crit value is not a build stat, and a scope it cannot honour is REFUSED | `critRate`/`critDmg` resolve once, before any hit exists, so a `damageTypes`-scoped crit grant has no home there — `stats.critRateBySkillType`/`critDmgBySkillType` hold it and `formula.js` adds it beside `typeDmg`, per hit. Two sonatas ship this shape and BOTH were paying every hit the wielder landed — and since 3.6 one WEAPON does too (Thousandfold Deliverance, 12% Crit Rate on Heavy, gated in the data on Nature's Order at 6 stacks via `ExtraEffectRequirements [12, 14]`), routed through the same `critScopeTypes` and the same wielder-only rule, and merged into `stats.js` from `weaponConditional` beside the sonata half: Flamewing's Shadow states 20% Crit Rate on Heavy and 20% on Echo Skill as two rows under one flat "20%" tooltip, and Sound of True Name's whole 20% is `damageTypes:[5]`. `sonataConditionalGrants` therefore leaves a scope it cannot express EXACTLY unclaimed, so the tier keeps its text rather than being widened — an element scope (no per-element crit bucket), a team-wide scope (that lane is whole-build), and an UNMAPPED damage tag. `critScopeTypes` refuses the WHOLE grant when ANY tag is unmapped, and refusing rather than filtering is the point: `scopeOf` in the same file builds `skillTypes` with `.filter(Boolean)`, and `targetModApplies` reads an empty `skillTypes` as "applies to every hit" — so a dropped tag WIDENS a scope instead of narrowing it. Only one unmapped tag exists in the data (sonata 9's `damageTypes:[7]`) and it carries attribute 15, so it reaches neither lane; both guards are prospective, and the `scopeOf` one is latent rather than live |
| A hit reads exactly ONE attack-type bucket, and it is not always `formulaType` | Three questions, not two (`core/dmg-attribution.js`): `skillType` is MECHANICAL (energy, cast, gating, `multiplierUp`), `formulaType` is ONE value **because it is also the skill-level key**, and the ATTRIBUTION is which DMG-type bucket the hit reads. The client settles that it is exactly one: `CharacterDamageCalculations.GetAttackTypeDamageBonus` is a `switch` on the instance's own `Type` with a single return — 0 `DamageChangeAuto`, 1 `Cast`, 2 `Ultra`, 3 `Qte`, 4 `NormalSkill`, 5 `Phantom` — folded in as `1 + Proto_DamageChange + elementBonus + attackTypeBonus`. So a `type 5` instance reads Phantom (Echo) and NOTHING else even when the move is mechanically a Heavy, and no code may ever SUM two of the six. 24 roster rows are attributed to echo ALONE, making their `formulaType` a mechanical stand-in: reading it as the attribution was wrong twice at once — measured, +50% in the mechanical bucket moved every one of them +50.0% (a bonus the game does not give them) while every Echo Skill DMG grant, including the ones Qiuyuan's and Lucilla's OWN kits state, missed them. All five per-hit sites take the resolved attribution: `formula.js` (DMG bonus + the per-type crit buckets), `resolveChainInherentContext`, a window's `dmgType`, outro amplify scopes, `targetModApplies` |
| A row tagged two ways is a MODE BRANCH, not a mixture | `dmgTypes` on a damage row records what the instance tags said, and two members means the game ships one instance per branch — never a hit that reads both. Lucilla's [Letting It Go] carries `1109014011` (Type 0) and `1109014012` (Type 5) with identical RateLv, element and energy, because her Resonance MODE decides which fires: the skill is Basic Attack DMG in Resonance Mode - Glacio Chafe and Echo Skill DMG in Resonance Mode - Echo. A mode is a build-level toggle locked for the fight, so `build.resonanceMode` resolves it (`attributionOf`), and a branch that cannot be resolved falls back to `formulaType` rather than guessing a half. 7 further rows span >1 non-echo type and state NO attribution — preprocess logs them and applies nothing, which is unchanged |
| A damage row's id must be unique WITHIN its resonator | `synId = rid*1e7 + nodeId*1000 + paramId` is NOT unique across the roster and never was — node ids are the game's own and reach 1.2e9, so the per-resonator bands overlap freely. Per-resonator uniqueness is the whole requirement, because `resolveSkill` only ever looks a row up inside `damageTable[resonatorId]` with `find(row => row.id === id)`. It was broken by SUFFIXED level-param keys (`15_2`, `29_5` — 22 of them across 12 resonators, marking a VARIANT row: a Hold version of a stage or a release-branch sub-move): `Number('15_2')` is NaN, NaN serialises to null, and every variant row of one resonator then shared the id `null`, so all of them resolved to the FIRST. Six of Chisa's seven read a stranger's multiplier (two of them 11.1x their own) AND its attribution. `paramIdOf` folds the suffix into the param NUMBER, never into the id formula, so every plain row keeps the id it has — the id is a join key |
| The attribution belongs to the ROW, not to the skill entry | A skillMap key can gather several damage rows (`damageIds.push`) and they need not share an attribution — Calcharo's `heavy_heavy_attack` ships one heavy-tagged row and one liberation-tagged row. A key-level field has to pick one and is then wrong for the other hit, which is also why a row's attribution may legitimately differ from its key's `formulaType` |
| A kit's OWN DEF ignore is an EFFECT, and unscoped it is inflation | Gear produces `context.defIgnore`/`resReduce` (external-buff `targetMods`) and one curated table does (`DEF_IGNORE_GRANTS`, Chisa), but a RESONATOR'S OWN kit clause reached nothing at all — **12 clauses across 9 resonators**, every one missing damage, and at level 90 vs 90 a 15% DEF ignore is x1.081 while Ciaccona S4's 45% is **x1.290**. They are emitted as ordinary effects (`effects.mjs` -> `resolveChainInherentContext` -> `skill.js`) rather than a curated table, which buys the whole existing pipeline: conditional gating, stack scaling, chain gating, and above all skill-name SCOPING — Lupa's clause names three skills and two of her Liberation keys are generically named, so hand-picking them would have been a guess where the binder is exact. They carry `needsScope`, for the same reason the "deals N% more DMG" branch does: unscoped and always-on, a DEF ignore multiplies every hit the wielder lands, and these clauses hide their conditions in prose the classifier does not read. **11 of 13 are DROPPED** — leaving today's understatement rather than replacing it with an overstatement — because the binder's forms all ended in the verb `increas` and these say `ignor`. ~~Widening it re-scopes EVERY stat roster-wide.~~ MEASURED: adding `ignor` to `INCREASED` and `ignores?` to `SUBJECT_FORM` moved **exactly 2 of 354 effects and re-scoped none** — "ignore" appears nowhere else in the kit vocabulary — so Lumi S2 (both Energized keys, +3.73%) and Lupa S6 (Climax + her named Intro, **+9.98%**) now bind. What still cannot bind is a clause scoped by CATEGORY rather than by name, because `resolveChainInherentContext` reads no `skillType` for this stat and `needsScope` therefore demands real keys: Ciaccona S4's "when dealing Resonance Liberation DMG" is a genuine category scope (45%, the largest missing value here), while Cantarella S6's `skillType` is the leading TRIGGER not the scope ("Casting Liberation makes Cantarella's DMG ignore 30%" covers ALL her damage), so honouring the category would silently narrow it — the two are indistinguishable without reading which. Qiuyuan S5 and Chisa S2 are genuinely whole-build and drop for want of any scope at all. Both binds are CHAIN-GATED, so LOCK B cannot see either (`team-rank.js` builds members at chain 0) — the same blind spot the Luuk S2 amplify bug had. A RES shred names the element whose RESISTANCE it removes and is gated on the hit's element; DEF is not an element and never is. `tests/conditional-effects.test.mjs` keeps unscoped always-on `defIgnore` at zero |
| DEF-ignore and RES-shred had no consumer | `contribution.defIgnore` existed for as long as the contribution shape has, and was read by NOTHING: `sim.js` consumed only the amplify buckets and `stats.js` mentions it only in empty-shape literals. `formula.js` has always had both hooks (`context.defIgnore`, `context.resReduce`); they simply had no producer. A RES shred is written by the game as a NEGATIVE value on the target's own resistance attribute (attr 30 = −0.10), not as an ignore attribute — so it lands in `resReduce`, not in a new bucket |
| Every surface measures against ONE enemy | `core/target.js` is the single definition (level 90, 10% RES on elements 1–6, physical always 0). The offline optimizer scored teams at **0% RES** while every UI surface simmed at 10%, so the build page's suggested-team card and the team page its own button opens could never agree — measured 2,599,423 dmg/pass against 2.41M, with the TIMES identical to the centisecond, which is the tell that only the enemy differed. A near-uniform ×0.93 reorders almost nothing (0 of 6 suggested builds and 0 of 6 weight sets moved; 1 of 52 anchors changed its top team, on a 1.2% margin), so this was never a ranking bug — it was two answers to one question, which is worse. Any new sim entry point takes its target from that module |

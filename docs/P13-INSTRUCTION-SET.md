## 1. The enumeration problem — why pruning is mandatory

Brute-forcing all 3-member teams is ~27,720 combinations. Even at the bare
config that's within budget time-wise, but it is wrong for two reasons:

1. **Compute**: realistic per-team cost (team-appropriate rotations × sonata
   variance × a team-level ER sub-sweep per team) multiplies 27k past any
   reasonable budget.
2. **Output quality** (the bigger reason): 27k ranked teams is useless. A player
   wants the ~10–20 teams that actually make sense for a character, not a team
   ranked #4,012. A precompute that emits everything emits noise.

**Resolution (agreed in design discussion): curated synergy hints prune the
space to plausible candidates, then the sim ranks those.** This is the
(c)→(a) approach from `PHASE0-ARCHITECTURE.md §1`: curated knowledge defines
*which* teams are worth simulating; the sim provides the *ranking*.

## 3. Synergy hints — `tools/optimize/synergy-hints.js` (the pruning table)

This is the curated knowledge that makes enumeration tractable. It encodes
*which* characters plausibly belong on a team together, so the enumerator only
generates candidates worth simulating.

### 3a. Shape

Hints are **pairwise affinities** and **role tags**, not full teams. Full teams
are generated by combining compatible pairs (§4), which keeps the table small
and maintainable (pairwise is O(roster²) at worst, but in practice sparse).

```js
// tools/optimize/synergy-hints.js

// Role tags: what function a character serves on a team.
export const ROLE = Object.freeze({
    MAIN_DPS:   'main_dps',
    SUB_DPS:    'sub_dps',
    HYBRID:     'hybrid',
    BUFFER:     'buffer',     // amplify/outro-buff support
    HEALER:     'healer',
    SUSTAIN:    'sustain',    // shield/sustain
    // Mechanic-specific roles (Tune Break, etc.)
    TB_SHIFTER: 'tb_shifter', // applies Shifting (Tune Break setup)
    TB_RESPONDER:'tb_responder', // responds to Interfered
    TB_BOOST:   'tb_boost',   // provides Tune Break Boost (effectively Mornye)
});

// Per-resonator role assignment. A character can have multiple roles.
export const CHARACTER_ROLES = Object.freeze({
    1107: [ROLE.MAIN_DPS],            // Carlotta
    1103: [ROLE.HEALER, ROLE.BUFFER], // Baizhi
    // ...
});

// Explicit synergy affinities — pairwise hints the enumerator trusts.
// affinity > 0 means "these two work together"; the magnitude is a curated
// prior, NOT the final score (the sim computes the real ranking).
// Encode the WHY in `reason` for the validation report and UI tooltips.
export const SYNERGY = Object.freeze({
    // Tune Break is the clearest example of mechanic-driven synergy.
    // Mornye provides Tune Break Boost + breaks; pairs with Strain responders.
    '1209+1510': { affinity: 3, reason: 'Mornye Tune Break Boost + Luuk Strain stacking' },
    '1209+1509': { affinity: 3, reason: 'Mornye + Lynae Rupture/Strain Shifting' },
    // Buffer + DPS element matches, etc.
    // Key format: '{lowerId}+{higherId}' (sorted, so lookups are canonical).
});

// Helper: canonical pair key.
export function pairKey(a, b) {
    const [lo, hi] = a < b ? [a, b] : [b, a];
    return `${lo}+${hi}`;
}
```

### 3b. Authoring discipline

- **Curated, dataset-verified** — same discipline as `rotation-rules.js`. Every
  character id referenced must exist in the dataset (enforced by a data-integrity
  test, §10).
- **Seed from mechanics first, meta second.** The strongest hints come from
  game mechanics the sim already models: buffers pair with DPS of the element
  they amplify; outro-buff providers pair with whoever benefits; Tune Break
  shifters pair with responders and the boost provider. Encode these because the
  sim can *verify* them. Softer "meta" pairings (community team comps) can be
  added but are lower-confidence.
- **Asymmetry is fine.** Mornye + Lynae is a strong hint; two main-DPS together
  is usually not. The table captures this naturally via role tags.
- **Coverage scope**: seed with the characters P12 covers (Carlotta, Hiyuki,
  Jinhsi, Changli, Phoebe, Cantarella) plus the 5 Tune Break characters
  (Mornye, Denia, Luuk Herssen, Lynae, Aemeath — the mechanic is the clearest
  synergy showcase). Expand later. Uncovered characters get no suggestions →
  runtime shows "no suggestion available" + live sim.

## 4. Candidate generation — `tools/optimize/team-enum.js`

Turns pairwise hints into full 3-member candidate teams, pruned hard.

### 4a. Generation rules

For a given **anchor character** (the one whose build page will show
suggestions), generate candidate teams:

1. Start with the anchor character in slot 1.
2. Collect all characters with a positive `SYNERGY` affinity to the anchor, OR
   with a complementary role (e.g. anchor is MAIN_DPS → pull BUFFER, HEALER,
   SUB_DPS candidates; never pair two MAIN_DPS unless a hint explicitly says so).
3. Form 3-member combinations from {anchor} ∪ {compatible characters},
   requiring:
   - At least one sustain/heal role OR an explicit hint overriding that
     (some teams skip healing).
   - No duplicate characters.
   - Total pairwise affinity above a threshold (drop teams where members don't
     mutually synergize — three characters who each pair with the anchor but
     not each other is usually weak).
4. **Cap the candidate count per anchor** (e.g. top ~30 by summed pairwise
   affinity) before simulation. This is the final prune — even after role
   filtering, cap to keep the sim pass bounded.

### 4b. Determinism

Candidate generation must be deterministic (sorted iteration, stable tie-breaks)
so the meta output is reproducible (same requirement as P12 §5a).

## 5. Team ranking + team-level ER — `tools/optimize/team-rank.js`

For each candidate team, run the full team sim and compute a ranking score.

### 5a. Per-team computation

For each candidate team:

1. **Assign team-appropriate rotations.** Each member uses their reference
   rotation from P12 (`referenceRotation` in the meta). Do NOT re-derive — reuse
   P12's artifact for consistency.
2. **Team-level ER sweep** (`PHASE0-ARCHITECTURE.md §5`). The character-level ER
   breakpoint from P12 assumed a solo context. In a team, energy sharing changes
   the requirement. For each member, sweep their ER within this specific team
   composition to find the team-context `minViable`, then apply the same +5%
   margin. Record the **team-level override** per member.
   - This is the key reason teams need their own ER number: a battery/energy-rich
     teammate can lower a DPS's ER requirement; an energy-hungry team raises it.
3. **Team damage total** from `simulateTeamRotation` at the resolved ER levels.
4. **Synergy score** = a normalized score combining team damage and the
   mechanic interactions that fired (e.g. Tune Break responses that actually
   triggered, outro buffs that actually applied). Store as a score, not a raw
   damage number, so it's comparable across anchors.

### 5b. What gets stored (the `teams` section of `wuwa-meta.json`)

Fill in the section `PHASE0-ARCHITECTURE.md §6` reserved:

```jsonc
"teams": {
  "byCharacter": {
    "1107": [                         // suggested teams for Carlotta, ranked
      {
        "members": [1107, 1103, 1506],
        "score": 0.91,                // normalized synergy+damage score
        "roles": ["main_dps","healer","sub_dps"],
        "reason": "Carlotta DPS + Baizhi heal/buff + Phoebe sub-dps",
        "erOverride": {               // team-level ER per member (§5a.2)
          "1107": { "minViable": 1.12, "recommended": 1.18 },
          "1103": { "minViable": 1.00, "recommended": 1.05 },
          "1506": { "minViable": 1.20, "recommended": 1.26 }
        }
      }
      // ... more ranked teams (capped, e.g. top 8-12 shown)
    ]
  },
  "appearsIn": {                      // reverse index for "appears in teams"
    "1103": [ {"anchor":1107,"members":[1107,1103,1506],"score":0.91} ]
    // for each character, which suggested teams include them
  }
}
```

`appearsIn` is derived from `byCharacter` — build it in the same pass so the
runtime "appears in teams" lookup is O(1).

### 5c. Storage scope

Store only the **top N ranked teams per anchor** (e.g. 8–12), not all simulated
candidates. The simulation evaluates ~30 candidates per anchor; only the best
survive into the file. Keeps `wuwa-meta.json` lean.

## 6. Orchestration — extend `tools/optimize.mjs`

Add a **team pass** after the existing P12 character pass:

```
(P12 character pass — unchanged: weights, breakpoints, validation)
(P13 team pass:)
for each covered anchor character:
  candidates = generateCandidates(anchor)        // team-enum.js
  ranked = []
  for each candidate:
    erOverride = sweepTeamEr(candidate)           // team-rank.js §5a.2
    score      = scoreTeam(candidate, erOverride) // team-rank.js §5a.4
    ranked.push({candidate, score, erOverride})
  keep top N → meta.teams.byCharacter[anchor]
build meta.teams.appearsIn from byCharacter
extend docs/meta-validation.md with the team section
```

Print team-pass progress separately from the character pass. The team pass is
the heavier of the two; make it observable and ideally resumable (per-anchor
partials), same as P12 §5c.

## 7. Runtime: team-level ER override — `src/core/team-er.js` (new)

Per `PHASE0-ARCHITECTURE.md §5`, the hybrid resolution: character-level ER is the
build-page default; the team-level value overrides it **when the character is in
a simulated team**.

```js
// resolveErTarget(resonatorId, sequenceLevel, sonataSetId, teamContext?)
//   teamContext = null  → return P12 character-level breakpoint (build page)
//   teamContext = {members:[...]} → if a matching team exists in
//       meta.teams, return its per-member erOverride; else fall back to the
//       character-level value (never leave the user without a number).
```

The team-sim screen (P11) and the comparison view (§9) use this to show the
*team-context* ER target. The standalone build page uses the character-level
default. Same character can show two different ER targets depending on context —
this is correct and should be explained in UI copy ("ER target in this team:
X%; solo target: Y%").

## 8. Runtime: build-page surfaces — `src/ui/components/build-editor.js`

### 8a. "Suggested teams" section

On a character's build page, show the ranked suggested teams from
`meta.teams.byCharacter[resonatorId]`:
- Each suggestion: the three members (portraits/names), the `reason`, the score
  (as a relative bar or rank, not a raw number — players read rank, not 0.91).
- Clicking a suggestion offers to **load it into the team simulator** (populate
  the three slots and jump to the team-sim screen).
- If the character is uncovered (`meta.teams.byCharacter[id]` absent): show
  "No team suggestions available for this character yet." Do not fabricate.

### 8b. "Appears in teams" indicator

Also on the build page, a compact list from `meta.teams.appearsIn[resonatorId]`:
"This character appears in suggested teams for: [Carlotta], [Jinhsi], …".
Each is a link to that anchor's build page. This is the reverse-lookup that
helps a player understand a support's value across the roster.

### 8c. Both surfaces degrade gracefully

If the meta file is absent/stale (meta-loader returns null per P12 §7), both
sections show a quiet "Team suggestions unavailable" rather than erroring.

## 9. Runtime: 3-way comparison — `src/ui/components/team-editor.js`

Per `PHASE0-ARCHITECTURE.md §8` (P11 built the single-team view to be composable
specifically for this).

### 9a. Layout

Up to **three team setups side by side**, each rendered with the P11 team-sim
visualization (per-character columns, step breakdown, buff bar). The comparison
adds a **shared comparison header** above the three:
- Team total damage (with the highest highlighted).
- Team DPS.
- Total heal/shield.
- A simple "winner" indicator on the top metric (clearly marked as "highest
  simulated total", not an absolute verdict).

```html
<div class="team-compare" data-teams="[1|2|3]">
    <div class="team-compare__col" data-compare-slot="0">
        <!-- a full P11 team-sim-grid instance for team A -->
    </div>
    <div class="team-compare__col" data-compare-slot="1"><!-- team B --></div>
    <div class="team-compare__col" data-compare-slot="2"><!-- team C --></div>
</div>
```

### 9b. Composition, not reimplementation

**Reuse the P11 single-team rendering.** The comparison view mounts three
instances of the existing `team-sim-grid` component. If P11 was built correctly
(self-contained, parameterized by a team object), this is mostly layout +
the comparison header. If you find yourself rewriting the step-bar or buff-bar
logic here, stop — that's a sign P11's component wasn't composable and the fix
belongs in the shared component, not duplicated here.

### 9c. What's comparable vs not

- Comparable directly: total damage, DPS, heal, shield (same single enemy, same
  target assumptions — `PHASE0-ARCHITECTURE.md` out-of-scope: enemy count is
  always 1, so comparisons are apples-to-apples).
- Show each team's **team-level ER targets** (from §7) so the user sees the
  energy cost of each option, not just the damage.
- Do NOT present a single "best team" verdict beyond "highest simulated total" —
  team choice depends on what the player owns, investment, and playstyle. The
  tool informs; it does not prescribe. (Consistent with the legal/advice-neutral
  posture and the "maximum user agency" principle.)

## 13. Hard requirements (do not compromise)

1. **Pruning is mandatory** — never brute-force all 27k teams. Curated hints
   gate which teams get simulated; the sim ranks the survivors.
2. **Team-level ER carries the +5% margin**, same as character-level (P12).
3. **Hybrid ER resolution** (`PHASE0-ARCHITECTURE.md §5`): character-level is the
   solo/build-page default; team-level overrides only in team context; fall back
   to character-level when no team match — never null.
4. **The comparison view composes P11's component** — no duplicated step/buff
   rendering logic.
5. **Uncovered → "no suggestion available."** Never fabricate a team.
6. **Stale meta treated as absent** (inherits P12 §7).
7. **No prescriptive "best team" verdict** beyond "highest simulated total" —
   maximum user agency; the tool informs.
8. **Single enemy always** — comparisons are apples-to-apples on that basis.
9. **Determinism** — same data + engine → reproducible `teams` section.
10. **The team QA section of the validation report is required** — the only
    practical loop for catching nonsense suggestions before they ship.

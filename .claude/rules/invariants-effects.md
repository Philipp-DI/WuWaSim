# Invariants — Effect-text parsing and scoping

Breaking any one silently corrupts sim output. Code comments cite these as
`CLAUDE.md, "<title>"`, so keep the titles stable.

| Invariant | Detail |
| --- | --- |
| An "is enhanced" chain node is PARTIAL, an "is replaced with" node is NOT | Both edit an inherent and they need opposite treatments. A REPLACEMENT restates the whole thing, so the inherent is suppressed entire (`replacedByChain`, Aemeath S3 — measured 3.152x vs the 3.452x of applying both). An ENHANCEMENT restates only PART of it, so suppressing the inherent would DELETE kit the node never touched: it is resolved per EFFECT (`supersededByChain`), matched on the (stat, element, skillType) triple so a differently-scoped grant survives, and only node effects whose OWN condition carries the enhancement phrase may supersede — a sequence node states several unrelated grants and one sharing a stat is coincidence, not restatement. Luuk Herssen S2 raises Uncaused Diagnosis 5% -> 10% amplify per 10 Tune Break Boost and both were live, so enabling both paid 15%. The inherent NAME is bounded to one sentence (`[^.]`): Lucy S5 names hers twice and an unbounded capture ran from the first mention to the second and resolved to nothing. A restatement the parser did not attach supersedes nothing, which leaves a pre-existing double-count rather than silently deleting kit — that is the safe failure direction |
| A LABEL'S LEADING CATEGORY is the move's KIND, and that is what resolves a category list | The trailing `· Forte Circuit` / `· Echo` marker is PROVENANCE; the leading category is what the game calls the move. That is the source to read a clause's category list off — not the node `skillType` (provenance-prefixed) and not the attribution (the bucket). Galbrena's Oathbound Hunt amplifies "Normal Attack, Resonance Skill, Forte Circuit, Resonance Liberation, Intro Skill, and Outro Skill": as BUCKETS that is nearly inert, since her kit reads only heavy/echo/intro/outro and four of the six have no hit at all; by LABEL it omits exactly ONE category, Heavy Attack, excluding all six Heavy keys (plain Volley of Death AND Forte Flamewing Verdict) and admitting the other 21. That is why such a list is written instead of "all her damage", and why "Forte Circuit" is not redundant in it: it is the catch-all for the Forte moves whose labels lead with Forte Circuit rather than another category. Reading the same list off node `skillType` gives a DIFFERENT and wrong split (it drops the mid-airs, whose label is "Basic Attack: Mid-air Attack — Ashfall Barrage", and keeps Flamewing Verdict) |
| Stack cap + gain trigger are DESCRIPTION-scoped | The game states them in the sentence that GRANTS the stack, not the "Each stack …" value sentence. `descStackCap`/`descStackGain` read the whole description and return null rather than guess when it is ambiguous |
| A skill's LABEL comes from the game's name, its TYPE from the node | The game files a move under the input that casts it, which is not always what it calls the move (Aemeath's Mech basic chain sits in her Resonance Skill node). When a row's own name opens with a category, that category wins the label; the mechanical `skillType` never changes. Prefixing the node's category produced 18 self-contradicting labels like "Resonance Skill: Basic Attack — Mech Stage 4". PROVENANCE — how the move is reached — is always a TRAILING `· Forte Circuit` / `· Echo` marker, never a parenthetical on the category: "Heavy Attack (Forte)" reads as "a Forte kind of Heavy Attack", which is backwards. It must still be SAID (Cartethyia's normal and Forte Basic stages collide into identical labels without it) |
| A clause that NAMES its skills is scoped by the NAMES | `tools/preprocess/skill-scope.mjs` binds both shapes the game writes — TARGET ("The DMG Multiplier of X is increased") and SUBJECT ("X and Y gain 300% Crit. DMG") — and the binding covers EVERY stat, not just `multiplierUp`. Once the names match they ARE the scope: the category read off the same clause is the weaker restatement and can contradict it outright (her Heavy Attacks are "considered Resonance Liberation DMG", so the clause parses `skillType: 'heavy'` while their hits carry `'liberation'`, and both gates together match nothing). A name that resolves to nothing leaves the effect exactly as it was, which is what keeps the pass safe — "Resonators in the team" resolves to nothing and stays team-wide. Safe is not the same as right, and the trap is that A SKILL'S OWN NAME LEADS WITH A CATEGORY WORD. The game writes "Resonance Liberation Rewritten in Winter's Margins"; `detectSkillType` lifts "Resonance Liberation" out of that and the effect ships `skillType: 'liberation'` — a category the sentence never stated, read off the NAME. When the name then fails to resolve, that invented category is all that is left, and it decides the effect's fate: Luuk Herssen S6.1 grants 40% DMG Bonus TO THAT NAMED SKILL (not to a bucket — a named grant pays whatever bucket the skill's hits read), the invented 'liberation' happened to be the one bucket his Liberation does NOT read (its instances are type 0, so the hit reads Basic — an ordinary Liberation CAST dealing Basic-bucket damage, correct and not a defect), and the effect measured ZERO even once triggered and stacked. Had the skill been named "Basic Attack …" the same mis-lift would have accidentally worked, which is the tell that the category was never load-bearing. NOT the Aemeath case: hers is a GENUINE contradiction between two real statements ("considered Resonance Liberation DMG"), this is one statement plus an artifact — same remedy, different cause. The binder cannot reach the key and that is ROSTER-WIDE: **30 resonators key their main Liberation as bare `liberation`** though its row label carries the skill's own name, so such a name has no token to match and `resolveNameToKeys` is structurally blind to all 30. Renaming the key is not the fix — it is the persisted `build.rotation` format. A SCOPE NO HIT CAN SATISFY IS DEAD BY ARITHMETIC whatever its value, and `tests/dead-scope.test.mjs` now audits both lenses for it with an allow-list that may only SHRINK — 8 dead today across 6 distinct causes, every entry carrying its investigated cause. **`'forte'` is never a scope on EITHER lens** and accounts for 4 of the 8: it is not an attribution tag (the game ships exactly basic/heavy/liberation/intro/skill/echo), and `nodeTypeMatches` strips `forte_` off the NODE type so `'forte'` is compared against `'heavy'` and fails too. It is a provenance prefix on a KEY and the word for a resonator's SPECIALTY — never a kind of damage. Rewriting it to the real bucket is NOT the fix: all five of Sigrika's Runic rows are tagged `echo` (stated twice, by `dmgTypes` AND her own "considered Echo Skill DMG"), but 10 of her keys read that bucket where her clauses name 4, so a category rewrite WIDENS the grant 2.5x. The scope is the NAMES. Auditing this requires resolving MODES: a `dmgTypes` pair is a branch, so Lucilla's echo scope is live under Resonance Mode - Echo and reads dead without one |
| A bare CATEGORY is not a skill NAME | Resolution matches a key on all of a name's distinctive tokens, so a name that is only a category resolves on a single blunt word — "Heavy Attack" reaches Cartethyia's `forte_heavy_mid_air_attack_*`, which are not Heavy Attacks. Such names are refused (`isBareCategory`) and the category travels through `skillType`/`nodeTypeMatches` instead, which strips the `forte_` provenance prefix properly. Safe only while `detectSkillType` can answer for the clause: refusing a category it does NOT read leaves the effect scoped to nothing, which is worse than the blunt match. That is why Brant's "Mid-air Attack**'s** DMG Multiplier" was fixed in `SCOPE_ONLY_PHRASE_TO_TYPE` (one possessive cost him his whole scope) and why `CATEGORY_TOKENS` holds no word that is distinctive in a real key |
| The scoping pass reads the FULL clause, not `condition` | `effects.mjs` stores `condition: clause.trim().slice(0, 120)` **for display**. 32 clauses are longer and the cut routinely removes the skill name — Xiangli Yao's "Law of Reigns" survives as the fragment "Resona". `bindSkillScopes` re-splits the node's own `desc` and matches on that 120-char prefix to recover the clause. Any new reader of `condition` that makes a DECISION (not a label) has the same bug: team-recipient detection had it once already |
| A list of casts that FIRE an effect is not its scope | The game writes a bulleted enumeration for both — "The following skills have their DMG Multiplier increased by 25%: - …" (Augusta, a scope) and "1 stack of Fated End is inflicted … when the following skills hit: - …" (Galbrena, a trigger). `BULLET_LIST_FORM` therefore requires the STAT in the preamble. A bulleted list is read ALL-OR-NOTHING, because a partial read drops members silently; and it runs PAST its own clause (the game ends a group with a period and opens the next with a bullet), so the continuation bullets must be gathered before the gate is applied |
| A trigger's category is not the effect's SCOPE | `SKILL_PHRASE_TO_TYPE` is read by `extractStructuralTrigger` (what fires it) AND `detectSkillType` (what it applies to). For a Tune Break the two are opposites — "After a Resonator deals Tune Break DMG, all Resonators deal 20% more DMG" is TRIGGERED by one and applies to EVERYTHING — so 'tuneBreak' is deliberately absent from that map and the trigger reads it from its own branch |
| The game states a DMG increase THREE ways, and the third was unread | "X deals N% more DMG" and "N% DMG Bonus" had branches; **"increases the DMG of X by N%" had none**, and all 3 roster clauses of it were silently unread. Two blockers, the second ONE CHARACTER: the parser needed a branch (emitting `dmgBonus` as a DEFAULT with `needsScope`, because the bucket is not recoverable from wording — `applyBuffFacts` runs BEFORE `bindSkillScopes` and corrects it from the game's tables while supplying the scope), and the binder needed `OF_BY_FORM`, because `OF_TAIL_FORM` reads names with `[^.;]` and **cannot cross the decimal point in the clause's own "1.5%"**. Measured: 107 bound (was 106), 12 dropped (was 13) — one extra binding, nothing re-scoped. The payoff was already sitting in the data: **Xiangli Yao S3's node held ZERO effects** while `buff-facts.json` had filed its bucket AND its exact four-key scope under 0.63 — one of the 40 orphaned ConfigDB scopes — so emitting the effect was all it took, worth **+34.34%** on his rotation and taking his S3 from +27.08% to +45.22% own. A CEILING implies a stack count only for a RESOURCE shape: "up to 60%" at 1.5%/point is 40 (Afterflame's own cap), but Jingran's "up to 2.5% FOR EACH STACK" divides just as tidily to 50 and 50 is not a count at all, so exact division alone is not the test — the ceiling must bound the same accumulation the per-unit value multiplies. `clearedOnSwap` is the narrow exception to "a gauge belongs to the CHARACTER": a kit that empties a gauge on a swap does not carry it between segments. **A FOURTH form exists and was unread too** — `INCREASE_FOR_FORM`, FOR_FORM's mirror with the verb BEFORE the stat: "Gain 85% DMG Multiplier increase for [A], [B], [C], and [D] for 14s". FOR_FORM needs `increas` AFTER the name and OF_FORM needs an "of", so the one roster clause of this shape (Galbrena's Liberation node) bound NOTHING and kept the category `detectSkillType` lifted off its first name — the Luuk S6.1 artifact again, and wrong in BOTH directions here: `'basic'` reached her five plain Basic keys, which the list does not name, and missed Flamewing Verdict and Hellsent Barrage, which it does. Measured: 108 bound (was 107), 12 dropped unchanged — one extra binding, nothing re-scoped, and the one effect is the only line of LOCK A that moved. **AND THE 5 IS A CHARGE POOL, NOT A STACK MULTIPLIER** — Xiangli Yao's "This effect can be triggered up to 5 times", verified against `db_buff` rather than reasoned from wording. His S3 is a three-link chain: `1305073001` root, requirement type **2 = SkillGenre** (`ExtraEffectLibrary.ResolveRequireAndLimits` `case 2`) para "3" = Liberation; `1305073003` carrier, 24s, `DefaultStackCount 5` = `StackLimitCount 5` with `ExtraEffectRemoveStackNum 1`, gated on SkillGenre "2" = Resonance Skill; `1305073002` payload, 1.5s, **`StackLimitCount 1`**, `ExtraEffectParametersGrow1 [6300]` on attribute 15 = the 63%. The buff carrying the value can never hold two, so he is NOT understated fivefold; the 5 is five Resonance Skill casts per Liberation window, and NOTHING has to reset it because the carrier is re-applied at 5 on every Liberation cast (`StackingType 2`, 24s against a 25s cooldown, so the windows never overlap). The flat model shipped is right for his rotation for a reason, not by luck: the payload is scoped to exactly the four skills that also TRIGGER it (the SkillGenre-2 members — 1305031 Divergence, 1305051 Deduction, 1305052 Decipher, 1305053 Law of Reigns), so every scoped hit re-applies its own 1.5s and "63% on those four keys while armed" IS the game. Its two boundaries: the sim arms on a Resonance Skill cast where the game arms on the LIBERATION (his rotation casts `skill` one step earlier, with no qualifying cast in between), and the 5-cap is unmodelled while his rotation lands **exactly 5** qualifying casts in the 24s. A rotation with six would overpay |
| A value may PRECEDE its stat, and the parser fails SILENTLY | The game writes a grant both ways — "Fusion DMG Bonus is increased by 30%" and "gain 30% Fusion DMG Bonus" — and a reader that only looks forward returns nothing at all, with no warning and no diff. 109 of 324 buff clauses were unread that way. `pctFor` reads either direction from a STAT NAME; `pctNear` stays forward-only from a VERB, because what precedes a verb belongs to a different effect in the same sentence. Every buff clause is now either read or listed with its reason in `tests/effect-coverage.test.mjs` — that list is the contract, and it may only shrink |
| A CAP restatement grants NOTHING, and the number after "instead of" is the DEAD one | The game raises a ceiling by restating it, and such a sentence carries no grant of its own. `pctFor` already skips a value behind "up to" for that reason — but it kept SCANNING past the ceiling and landed on the superseded value after "instead of", which is the one number in the sentence that is certainly not the grant. Luuk Herssen S2 ("This effect now increases the DMG Amplification up to 60% instead of 30%") therefore shipped a permanent, unconditional, unscoped **+30% amplify across his whole kit** — measured **x1.3000 on every hit at S2+**. Only two roster sentences use "instead of" and they need OPPOSITE halves of that loop: Phoebe S1 grants the 480% of "by 480% instead of 255%" (unprefixed, so it still wins), while Luuk's has EVERY number behind a cap word and must read as nothing. The rate and the ceiling MOVE TOGETHER — the same S2 sentence pair also raises `INTERFERED_SELF_AMPLIFY`'s cap 30% -> 60%, and reading only the rate paid him 30% where he earned 40%. `tests/multiplier-scope.test.mjs` guard 3 keeps always-on cap-only clauses at zero. Invisible to LOCK B by construction: `tools/optimize/team-rank.js` builds every team member at **chain 0**, so no S2-gated defect can ever move the meta |
| A sentence's leading TRIGGER is not the effect's SCOPE | The game names the cast that fires a buff before it names the buff: "After casting Intro Skill Applaud for Me!, Brant's DMG dealt is increased by 20%" is not an Intro-only buff, and "Casting Heavy Attack Mercy gives Calcharo 10% Resonance Liberation DMG Bonus" is not a Heavy one. Scope comes from the segment that OWNS the stat — `ownerSkillType` (last comma-free run before the verb) and `statScopeSkillType` (the words right in front of the stat phrase) — never from `detectSkillType` over the whole clause |
| An Outro Skill has NO level curve | Its `level` map is empty, so the row loop walks zero params and produces nothing — which is why 55 of 56 resonators shipped with no outro damage row and every swap scored 0. The multiplier is read from the sentence that STATES it and repeated across the level band. A resonator whose off-field actions carry an `outro` trigger (Galbrena, Calcharo, Rover: Havoc) must NOT also cast one: two paths, one cast |
| A mode-gated outro is a MENU, not one grant | "When in Resonance Mode - A, …. When in Resonance Mode - B, …" is two grants with their own values AND their own durations, of which exactly one is live. Read flat, Denia's outro took the value from one branch and the duration from the other and handed the mix to every build. Branches carry `outroBuffs[*].mode`, filtered at the hand-off against the OUTGOING member's `build.resonanceMode` |
| An element word before "DMG" may name a STATUS | "Fusion Burst DMG", "Glacio Chafe DMG" and "Aero Erosion DMG" open with an element but mean the negative status's own damage — a separate formula with no crit and no gear stat. The outro scope map matches the element only with "DMG" IMMEDIATELY after it, which is what keeps Denia's, Lucilla's and Ciaccona's outros out of the wielder's amplify bucket |
| "The incoming Resonator gains …" is the OUTRO lane's, and the second copy is MARKED not dropped | An Outro Skill's grant goes to the member switching IN and `outroBuffs` already carries it, but the same sentence also reaches the ordinary effect parser, which knew only "the wielder" or "the team" — so it emitted a SECOND copy as a SELF buff. Measured: exactly **4 clauses** on the roster say this (Iuno, Qiuyuan, Lynae ×2) and every one is already in its own `outroBuffs` at the same value and the same 14s; none is a distinct grant. None was paying, but three were LATENT: Iuno's trigger fires and its window opens, with only a dead scope stopping it, so repairing that scope would have switched on a 50% self-amplify. `effects.mjs` stamps `recipient: 'incoming'` (`INCOMING_RECIPIENT_RE`) and `resolveChainInherentContext` skips it. **MARKED, NEVER DROPPED** — deleting an effect changes its node's effect COUNT and re-slots every `S{level}.{index}` after it, and Lynae carries a curated override at `S3.1` directly after one of these at `S2.1`. `tests/dead-scope.test.mjs` exempts the flag for the same reason it exempts `teamWide`: the WIELDER'S kit is the wrong kit to ask of a buff paid to someone else |
| A NEGATIVE STATUS'S OWN DAMAGE is not the wielder's, and reading it as such INFLATES | "Glacio Chafe DMG", "Fusion Burst DMG", "Aero Erosion DMG" open with an element or a mechanic but name the STATUS, whose damage has its own formula. **Denia S6 shipped "The Fusion Burst DMG triggered gains a 200% DMG Multiplier increase" as an UNSCOPED `multiplierUp` of 2.0 with `window: always`, multiplying her ENTIRE kit — measured x1.737 (85,304 -> 49,104) and `sequenceEval` ownGain +498% -> +194%** — because she has no `AFFLICTION_TRIGGERS` entry for it to live in. `effects.mjs` stamps `statusGrant` (`statusGrantIn`) and `resolveChainInherentContext` skips it; the name must be followed IMMEDIATELY by "DMG", which keeps her own "60% Fusion DMG Bonus" two lines above out of it. **A STATUS BEHIND A DEALING VERB IS THE TRIGGER, NOT THE SUBJECT** — the first draft lacked that test and marked 11 clauses where 8 are grants, three of them Aemeath's own Crit DMG and amplify granted "when Resonators in the team ... deal Tune Rupture DMG", which it would have DELETED. Skipping UNDERSTATES, which is the safe direction, and is temporary: the value is recorded for a producer that does not exist yet. VALIDATED EXTERNALLY, and the validation says she is now UNDER: arabwuwa puts Denia's S6 at 339% of S0 in Fusion Burst mode, the sim was 598% before and is 294% after, so the 2.0 was over-compensating for her Erosion Field -> Fusion Burst chain, which is modelled NOT AT ALL (her S4 scores a gain of exactly zero where the reference has +6%). Its real home is an `AFFLICTION_TRIGGERS` entry: the 2.0 applies only to the Fusion Burst instance triggered by Erosion Field DMG, with its own internal cooldown (maintainer, 2026-10-03) |
